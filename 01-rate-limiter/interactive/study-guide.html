Concept

What a rate limiter is

A rate limiter caps how many requests a client can make in a given time. Requests within the limit go through. Requests over it are rejected (HTTP 429 Too Many Requests, RFC 6585), queued, or slowed down. It sits in front of your service and answers one question per request: allow or block?

Real example: GitHub's REST API allows 5,000 requests per hour for an authenticated user and 60 per hour unauthenticated. Every response tells you how many you have left.

Why it exists

  • Abuse and DoS: stops one client from flooding you, whether it's a bot, a scraper or a buggy retry loop.
  • Fairness: stops one noisy tenant from slowing everyone else down (the noisy-neighbour problem).
  • Cost control: every call to a paid downstream (SMS, payments, LLM tokens) costs money. A limit caps the bill.
  • Protecting weaker systems: a database or legacy service has a fixed capacity, and the limiter keeps traffic under it so it doesn't fall over.
  • Security: it slows brute-force attacks, such as login attempts and OTP guessing.

Related terms you'll be asked to tell apart: rate limiting rejects a client over its quota, throttling slows a client down, and load shedding drops requests when the server itself is overloaded, whoever sent them.

Interview step 1

Requirements

Functional

  • Limit by a key: user ID, API key, IP or endpoint
  • Rules are configurable, e.g. 100 req/min per user, 5 req/min on /login
  • Rejected callers get a 429 plus headers saying when to retry
  • Several rules at once, e.g. per second and per day

Non-functional

  • Low latency: the check runs on every request, so it must cost about a millisecond
  • Accurate across many servers (the hard part)
  • Highly available: if the limiter dies, the API shouldn't
  • Memory-efficient: millions of keys

1 · Fixed window counter

used for: daily / monthly quotas

Cut time into fixed windows (0–10 s, 10–20 s, …). Keep one counter per key per window. Increment the counter on each request and reject once it passes the limit. When a new window starts, the count is back to zero.

Pros

  • One integer per key, so the cheapest option
  • INCR is atomic in Redis
  • Easy to explain and reset

Cons

  • 2× burst at window edges
  • A thundering herd when every client's window resets at :00
// Redis version
allow(key, now):
  win   = floor(now / W)
  k     = key + ":" + win
  count = INCR(k)                 // atomic
  if count == 1: EXPIRE(k, W)     // ⚠ crash between INCR and EXPIRE → key never expires → user blocked forever
  return count <= LIMIT

2 · Sliding window log

used for: strict, low-volume limits (login, OTP)

Store the timestamp of every allowed request. On each new request, delete timestamps older than now − 10 s and count what's left. If the count is under the limit, allow the request and add its timestamp. The window slides with the clock, so there's no boundary to exploit.

Pros

  • Exact: never more than the limit in any 10 s span
  • No boundary burst

Cons

  • Memory grows with the limit: 1,000 req/hr = 1,000 timestamps per user
  • Check-then-add is a race across servers, so it needs Lua
// Redis sorted set: score = timestamp
allow(key, now):
  ZREMRANGEBYSCORE(key, 0, now - W)   // drop old entries
  if ZCARD(key) < LIMIT:
    ZADD(key, now, uniqueId)
    EXPIRE(key, W)
    return true
  return false                       // ⚠ two servers can both see 4 and both add → 6

3 · Sliding window counter

used by: Cloudflare

A cheap approximation of the sliding log. Keep only two counters: the previous window and the current one. Estimate the count over the last 10 s by assuming the previous window's requests were spread evenly across it:

estimate = prev × (1 − elapsed/W) + curr

Pros

  • Two integers per key, so it's cheap
  • Smooths out the boundary burst
  • Accurate enough at large scale

Cons

  • An approximation: it assumes the previous window was uniform
  • Harder to explain to your team (and to viewers)
allow(key, now):
  cur     = floor(now / W);  elapsed = (now mod W) / W
  prev    = GET(key:cur-1) or 0
  curr    = GET(key:cur)   or 0
  if prev * (1 - elapsed) + curr >= LIMIT: return false
  INCR(key:cur);  EXPIRE(key:cur, 2 * W)
  return true                        // ⚠ read-then-write again → Lua for exactness

4 · Token bucket

used by: Stripe, AWS API Gateway

A bucket holds up to capacity tokens (here 5). Tokens drip in at a fixed refill rate (here 0.5 per second). Each request takes one token, and an empty bucket means 429. The capacity sets the largest allowed burst and the refill rate sets the long-run average.

Key implementation insight: there's no background timer adding tokens. Store tokens and last_refill, and on each request compute the refill as (now − last) × rate. That's two numbers per key and no cron job. Say this in the video, because most explainers skip it.

Pros

  • Allows short bursts, which is how real clients behave
  • Two values per key
  • Two knobs that are easy to reason about: burst and average
  • The default choice for public APIs

Cons

  • Two parameters to tune per rule
  • The read-modify-write needs Lua when it's distributed
  • A full bucket lets a burst hit the backend at once
allow(key, now):
  {tokens, last} = HGETALL(key) or {CAPACITY, now}
  tokens = min(CAPACITY, tokens + (now - last) * RATE)   // lazy refill
  if tokens < 1:
    return {false, retryAfter: (1 - tokens) / RATE}
  HSET(key, tokens - 1, now)
  return true                        // ⚠ the bug Part 2 breaks on screen

5 · Leaky bucket

used by: Shopify REST API, NGINX limit_req

Requests go into a fixed-size FIFO queue (the bucket). A worker takes them out at a constant rate (here 1 every 2 s), like water leaking from a hole. If the queue is full, new requests are dropped. However bursty the input is, the output is perfectly smooth.

Pros

  • Smooth, predictable output, ideal in front of a fixed-capacity system
  • Memory is bounded by the queue size

Cons

  • Bursts are delayed rather than served, which adds latency
  • Old requests at the front can starve fresh ones
  • Needs a worker or queue, not just a counter

Interview nuance: "leaky bucket" means two things. As a queue (shown here) it shapes traffic. As a meter it's a counter that drains at a fixed rate, which is the mirror image of token bucket. Shopify's API uses the meter form: a bucket of 40 that leaks 2 per second.

on request:
  if queue.size >= CAPACITY: return 429
  queue.push(request)

worker (every 1 / RATE seconds):
  req = queue.pop();  process(req)

Distributed design

From one server to many

With one server, a hashmap in memory is fine. With 10 servers behind a load balancer, each has its own hashmap, so a user gets 10× the limit. Counters must live in a shared, fast store. Redis is the standard answer: in memory, about a millisecond away, with atomic INCR, TTLs and Lua scripts.

Problems this creates (the senior-level part)

  • Race conditions: read-check-write from 2 servers lets both through. Fix it with a Lua script, which Redis runs atomically. See the stepper below.
  • Latency: every request now makes a network hop. Keep Redis close, use one round trip (Lua), and pool connections.
  • Redis goes down: fail open (allow everything, keeping the API up) or fail closed (reject everything, keeping the backend safe). Most public APIs fail open. A limit protecting money or a fragile system may fail closed. Say which and why.
  • Clocks: app servers disagree on the time. Use one clock, either Redis's TIME inside the script or a single trusted source.
  • Hot keys: one huge tenant hammers one Redis shard. Shard by key, and for giants keep a local pre-limit that syncs to Redis in batches.
  • Multi-region: one global counter is slow. Use per-region limits (global ÷ regions) or sync asynchronously and accept a small overshoot.

    Interview extras

    Follow-ups interviewers ask

    • Limit by what? By IP, a whole office behind one NAT shares a limit. By user, logged-out traffic isn't covered. Real systems layer these: IP for anonymous traffic, API key or user for authenticated.
    • Tiered limits: free gets 100/min, paid gets 1,000/min. Rules live in config, keyed by plan, and are cached in the gateway.
    • Multiple rules: 10/sec and 10,000/day. Check all of them; any one can reject.
    • What does the client do with a 429? Honour Retry-After, back off exponentially with jitter. Without jitter, every client retries at the same instant (links to the retry-storm video).
    • Headers: Retry-After is standard (RFC 9110). X-RateLimit-* is a de-facto convention, and the IETF is standardising RateLimit headers in a draft.
    • Hard vs soft limits: a soft limit lets a request through but logs or alerts. Useful when rolling out a new limit to see who would be hit.
    • Observability: track the rejection rate per rule and per tenant. A sudden spike means either an attack or a limit set too low.
    Part 2

    Build plan

    Every algorithm implements the same interface, so they can be swapped and compared:

    allow(key) → { allowed: bool, remaining: int, retryAfterSeconds: float }
    1. Five in-memory limiters, about 20 lines each, with unit tests that drive a fake clock (no sleeping in tests).
    2. Traffic replayer: the same request pattern (steady, burst, edge attack) into all five, printed as a side-by-side allowed/rejected chart. This is the money shot for the comparison.
    3. HTTP middleware: a tiny API that returns 429 plus the headers. Flood it with hey or k6.
    4. Move the token bucket to Redis the naive way: GET, compute, SET.
    5. Break it: 2 server processes behind NGINX, 200 concurrent requests, count the 200s, and get more than the limit.
    6. Fix it: a Lua script of about 15 lines. Rerun and the count equals the limit.
    7. Bonus break: the fixed-window INCR + EXPIRE crash bug. Kill the process between the two calls, and the key has no TTL, so the user is blocked forever.
    8. Bonus: kill Redis and show fail-open vs fail-closed behaviour.
