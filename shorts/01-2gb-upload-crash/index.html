2 GB upload crashes the server

“A user uploads a 2 GB file and your server crashes within seconds. How do you handle this in production?”

1 · Must-know

Why the server dies

Three things run out, usually in this order:

ResourceWhat happensNumbers
MemoryCode reads the whole body into RAM: file.getBytes(), readAllBytes(), Express multer.memoryStorage().2 GB per upload. 10 users at once = 20 GB → OutOfMemoryError.
ThreadsThe request keeps a worker thread busy for the whole transfer.2 GB = 16,000 Mb. At 20 Mbps: 800 s ≈ 13 min per upload.
Disk / bandwidthBig bodies spool to /tmp; the proxy may buffer them too. Every byte crosses your network card twice.In from the user, out to storage.

IMPIt's not a storage problem, it's a “who carries the bytes” problem. While the 2 GB flows through your app server, a bigger machine only moves the limit.

2 · Must-know

The four fixes, in order of impact

① Streaming (if bytes must pass through you)

Read the body as an InputStream and pipe it onward in small chunks. Memory = buffer size, not file size. Fixes RAM only: the 13-minute thread hold and double bandwidth stay.

IMP② Presigned URL: direct upload

The server only checks “is this user allowed?” and signs a short-lived URL for one exact object key. The browser uploads straight to S3 (or GCS / Azure Blob). Your server handles two tiny JSON calls instead of 2 GB. Fixes RAM, threads, bandwidth and cost together.

③ Multipart upload

Split into parts (e.g. 2 GB → 21 parts of 100 MB) and upload them in parallel. A network drop costs one part, not the whole file. Resume is possible. Try it in the simulator below.

④ Async processing

When the upload completes, S3 fires an event → queue → worker does virus scan, transcode, thumbnails. The user sees “Processing…” instead of a hanging request.

3 · Interview traps

Answers that sound right but aren't

“Just increase max-file-size to 2 GB.”

That removes a guard. Spring Boot's defaults are max-file-size=1MB, max-request-size=10MB on purpose. Raising them without streaming invites the crash.

“Use S3.”

If the bytes go browser → your server → S3, S3 changed nothing about RAM, threads or bandwidth. Say direct upload.

“Presigned URLs are secure.”

A presigned URL is a bearer token: anyone holding it can use it, many times, until it expires. Keep expiry short (5–15 min), scope it to one server-chosen key, never let the client pick the path. S3 silently replaces an existing object with the same key.

“The UI blocks files over 2 GB.”

A presigned PUT doesn't cap size by itself. Use a presigned POST with ["content-length-range", min, max], or presign each part (part count × part size caps the total). Always verify with HeadObject after upload.

“Client said upload done, so it's done.”

Never trust it. Check the object exists, the size matches what you approved, and the checksum matches (SigV4 supports CRC32, CRC32C, SHA-256 and more).

“Streaming solves it.”

Memory only. The thread is still held for ~13 minutes and every byte still crosses your network card twice. Try “Stream through server” in the crash simulator with 500 users.

“URL expires mid-upload → upload breaks?”

No. S3 checks expiry when the request starts. A part that started before expiry finishes. A retry after expiry fails, so the client asks for a fresh URL.

4 · Production depth

Limits you hit before your code even runs

LayerLimit
nginxclient_max_body_size default 1m → 413. proxy_request_buffering on (default) reads the whole body before passing it on; set off on streaming upload routes.
AWS API GatewayMax payload 10 MB
AWS LambdaSync request payload 6 MB
CloudflareRequest body cap 100 MB on Free/Pro plans
JavaA byte[] holds at most ~231 bytes (~2 GiB), so getBytes() on a 2+ GiB file fails even with free heap

IMPThese limits are why serverless and CDN-fronted apps must upload directly to storage. There is no “just make it bigger” option.

Abandoned uploads cost money

Parts of a multipart upload that never completes stay in the bucket and are billed. Add a lifecycle rule AbortIncompleteMultipartUpload (e.g. DaysAfterInitiation: 1).

Resume after the user closes the laptop

  • S3: store the uploadId; ListParts returns which parts already landed; upload only the rest.
  • tus protocol (open standard): HEAD returns Upload-Offset (bytes the server has); the client PATCHes the rest from that offset. Used by Vimeo, Cloudflare Stream, Supabase.

Choosing part size

  • More parts = finer retries, more requests. Fewer parts = bigger retries.
  • 2 GB: 64–100 MB parts. Minimum 5 MiB, max 10,000 parts, so a 1 TB file needs parts of at least ~100 MB.
  • 3–6 parallel parts per client is usually enough; more just shares the same uplink.

Security pipeline

  • Check the real type from the file's bytes (magic number), not the extension or client Content-Type.
  • Unzip/process inside size and time limits (zip bomb: 1 KB archive → GBs).
  • Rate-limit the “create upload” endpoint per user so nobody farms URLs to fill your bucket.
  • Downloads mirror the problem: serve with a presigned GET or a CDN, never through the app.

Other stacks, same trap

  • Node/Express: multer.memoryStorage() = whole file in RAM; use disk storage or stream with busboy. express.json() default limit is 100 kb.
  • Python: Django keeps uploads under 2.5 MB in memory, bigger ones go to a temp file; FastAPI UploadFile spools to disk past ~1 MB. Fine for medium files, still wrong for 2 GB through the app.

6 · Self-quiz

Check yourself (tap to reveal)

1. Streaming is in place and memory is flat, but the server stops accepting requests during big uploads. Why?

Each upload still holds a worker thread for the whole transfer (~13 min for 2 GB at 20 Mbps). A few concurrent uploads exhaust the pool.

2. You hand out a presigned PUT URL valid for 1 hour. What two things can go wrong?

Anyone with the URL can upload, repeatedly, until expiry (bearer token). And a plain PUT doesn't cap size. Fix: short expiry, server-chosen key, POST policy with content-length-range or per-part presigning, verify with HeadObject.

3. A 2 GB upload in 20 parts fails at part 14 because the network dropped. What does the client re-upload?

Only part 14 (plus any parts in flight), using the same uploadId. ListParts tells it which parts S3 already has.

4. Your S3 bill keeps growing but the object count doesn't. Likely cause?

Incomplete multipart uploads: their parts are stored and billed but never become objects. Add an AbortIncompleteMultipartUpload lifecycle rule.

5. Your app runs on Lambda behind API Gateway. Can you accept a 2 GB upload with streaming?

No. API Gateway caps payloads at 10 MB and Lambda's sync payload at 6 MB. Direct-to-S3 with presigned URLs is the only option.
