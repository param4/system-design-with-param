2 GB upload crashes the server

“A user uploads a 2 GB file and your server crashes within seconds. How do you handle this in production?”

A common backend interview question. This page explains why the crash happens, the four standard fixes, the traps interviewers set, and what changes in real production systems. No prior AWS knowledge needed: every term is explained the first time it appears.

Quick glossary

RAM / heapThe server's working memory. In Java the program's share of it is called the heap. If the program asks for more than it has, it crashes with OutOfMemoryError.
Thread, thread poolA thread is one worker inside the server that handles one request at a time. Java servers keep a fixed number of them (the pool, e.g. Tomcat's default of 200). If all are busy, new requests wait. Node.js works differently (one event loop); see the Node box in section 1.

Multipart uploadUploading one big file as many smaller pieces (parts) that S3 joins back together at the end.

1 · Must-know

Why the server dies

Picture the simplest upload endpoint: the browser sends the file to POST /upload, the server reads the whole file, then saves it to S3. It works perfectly in testing with a 2 MB photo. With a 2 GB video, three things go wrong:

1. Memory runs out

Code like file.getBytes() (Java), readAllBytes(), or multer.memoryStorage() (Node) copies the entire file into RAM before doing anything with it.

Example: one 2 GB upload needs 2 GB of RAM. If 10 users upload at the same time, that's 20 GB. A typical server has 4–16 GB, so it crashes with OutOfMemoryError, and every other user's request dies with it.

2. Threads get stuck

While a file is uploading, the thread handling that request can't do anything else. Uploads are slow, so threads stay busy for a long time.

Example: how long does 2 GB take on a 20 Mbps home connection?
2 GB = 2,000 MB → × 8 bits = 16,000 Mb → ÷ 20 Mb per second = 800 s ≈ 13 min.
So each upload holds one thread for ~13 minutes. With a pool of 200 threads, 200 people uploading at once leaves zero threads for login, search or anything else.

3. Disk and network fill up

Many frameworks save big uploads to a temporary folder (/tmp) first, which can fill the disk. And every byte crosses your server's network twice: once coming in from the user, once going out to S3. You pay for that bandwidth and it slows everything else down.

What about Node.js? It has no thread pool per request

Java servers (Tomcat, Spring) give each request its own thread from a pool of ~200. Node works differently: one main thread, the event loop, juggles all connections. Reading from the network doesn't block it, so a slow upload does not hold a thread. But the same three resources still run out, in a different shape:

ProblemJava (thread per request)Node (event loop)
Slow 13-min uploadHolds 1 of ~200 threadsHolds 1 open connection (a socket). The OS caps open connections per process, often around 1,024 by default
Whole file in memorygetBytes() → OutOfMemoryErrormulter.memoryStorage() or collecting the body into a Buffer → process crashes (heap out of memory)
Heavy work on the fileBlocks only that one threadBlocks everyone: synchronous code like fs.readFileSync or hashing a 2 GB buffer freezes the single event loop, so every user waits
Disk writes, crypto, zipDone on the request threadSent to libuv's background pool (libuv is Node's I/O library), only 4 threads by default (UV_THREADPOOL_SIZE). Many uploads writing to disk queue up behind those 4

IMPNode-only trap: since Node 18, the HTTP server's requestTimeout defaults to 300 seconds. A 13-minute upload is cut off at 5 minutes, unless you raise it. One more reason to upload directly to S3.

IMPThe real problem isn't storage, it's who carries the bytes. As long as the 2 GB has to pass through your app server, a bigger server only raises the limit; it doesn't remove it. The best fix is to make sure the file never touches your server at all.

2 · Must-know

The four fixes, from weakest to strongest

① Streaming

What it is: instead of reading the whole file and then saving it, the server reads a small chunk (say 8 MB), forwards it to S3, then reads the next chunk, like passing buckets along a line instead of filling a swimming pool first.

What it fixes: memory. Each upload now uses only one chunk's worth of RAM, no matter how big the file is.

What it doesn't fix: the thread is still busy for the full 13 minutes, and the 2 GB still crosses your network twice.

IMP② Presigned URL: upload directly to S3

What it is: the browser first asks your server, “may I upload this file?” Your server checks the user is logged in and allowed, then creates a presigned URL: a normal-looking S3 link with a signature attached. The browser uploads the file straight to S3 using that link. Your server never sees the 2 GB.

Analogy: a gate pass. Security (your server) doesn't carry your furniture into the building; it writes you a signed pass that says “flat 42 only, valid until 6 pm”. The building (S3) checks the signature and lets you in.

What's inside the link: which bucket and file path it's for, whether it allows upload or download, an expiry time, and a signature made with your server's AWS credentials. Change any of these and S3 rejects it.

How long can it last? It can never outlive the credentials that signed it:

  • Signed with a permanent access key (an IAM user's key): up to 7 days, AWS's maximum.
  • Signed with temporary credentials, which is what servers normally use (an IAM role on EC2, ECS or Lambda): the link dies when those credentials expire, often within 1–6 hours, even if you asked for 7 days.
  • In practice set it to 5–15 minutes. Anyone who gets hold of the link can use it until then.

What it fixes: memory, threads, bandwidth and cost, all at once. Your server only handles two tiny requests (“may I upload?” and “I'm done”).

③ Multipart upload

What it is: split the file into parts and upload several at the same time. Example: 2 GB with 100 MB parts = 21 parts; upload 4 at once.

Why it matters: if the Wi-Fi drops while part 14 is uploading, only part 14 is sent again (100 MB), not the whole 2 GB. If the user closes the laptop, the upload can resume from the parts already done. Parallel parts also use the connection better.

S3 needs this anyway above 5 GB, the most a single upload request can carry. Try it in the simulator below.

④ Async processing

What it is: after the upload, the file usually needs work: virus scan, video conversion, thumbnails. Instead of doing that inside the request (making the user wait), S3 sends an “object created” event to a queue, and a background worker does the job.

What the user sees: “Uploaded ✓ · Processing…” immediately, then a notification when it's ready.

2 · Must-know

The full flow: presigned multipart upload

This is the complete answer an interviewer wants. Only the green arrows carry the actual file, and none of them pass through your API server.

  1. Client → API: “I want to upload video.mp4, 2 GB, type video/mp4.” Sending the size and type first lets the server reject a bad file before a single byte is uploaded.
  2. API → S3: CreateMultipartUpload. S3 opens an upload session and returns an uploadId, a ticket number that ties all the parts together. The server picks the file path, e.g. uploads/{userId}/{random-id}, so a user can't overwrite someone else's file.
  3. API → Client: one presigned URL per part (21 URLs for 2 GB in 100 MB parts). These are a few KB of text.
  4. Client → S3: uploads the parts in parallel using those URLs. For each part S3 replies with an ETag (that part's fingerprint); the client keeps the list.
  5. Client → API: “all parts done, here are the 21 ETags.”
  6. API → S3: CompleteMultipartUpload. S3 stitches the parts into one file.
  7. API → S3: HeadObject. Reads the stored file's details (size, checksum) to confirm it really is the file the user said it was. Never trust the client's word alone.
  8. S3 → Queue → Worker: the “object created” event triggers the scan and processing in the background.

3 · Interview traps

Answers that sound right but aren't

“Just increase max-file-size to 2 GB.”

Why it's wrong: Spring Boot rejects files over 1 MB by default (max-file-size=1MB, max-request-size=10MB). That limit is a safety guard. Raising it to 2 GB doesn't make the server able to handle 2 GB; it just lets the 2 GB in, and then the memory problem crashes it.

Say instead: keep the guard on the API, and send big files directly to S3.

“Store it in S3.”

Why it's incomplete: if the file still goes browser → your server → S3, your server still holds the RAM, the thread and the bandwidth. S3 only changed where the file ends up.

Say instead: upload directly from the browser to S3 with presigned URLs.

“Presigned URLs are secure.”

Why it's risky: a presigned URL works like cash. Whoever holds it can use it, as many times as they like, until it expires. Nobody checks who is using it. If it leaks (logs, browser history, a shared screenshot), someone else can upload.

Say instead: short expiry (5–15 min), one exact file path chosen by the server, and never let the client choose the path, because S3 silently replaces an existing file with the same path.

“The frontend blocks files over 2 GB.”

Why it's wrong: anyone can skip your frontend and call S3 directly with the URL. And a plain presigned upload URL doesn't limit size by itself.

Say instead: enforce the limit in what you sign. Either a presigned POST with a content-length-range rule (S3 rejects files outside that range), or presign a fixed number of parts (21 parts × 100 MB can't exceed ~2 GB). Then check the real size with HeadObject after upload.

“The client said it's done, so it's done.”

Why it's wrong: the client could be buggy or malicious. It might claim a 2 GB video and upload a 5 KB script.

Say instead: after completion the server checks with S3 that the file exists, has the approved size, and its checksum (a hash of the content) matches.

“Streaming solves it.”

Why it's incomplete: streaming fixes memory only. The thread is still busy for ~13 minutes per upload and the bytes still cross your network twice.

Say instead: streaming is the fallback when bytes must pass through you; direct upload is the real fix.

“What if the link expires mid-upload?”

S3 checks the expiry only when a request starts. A part that started before expiry will finish. But if a part fails and is retried after expiry, S3 rejects it, so the client asks your server for a fresh URL for that part.

4 · Production depth

Limits you hit before your code even runs

In production your app sits behind several layers (CDN, proxy, gateway). Each one has its own default size limit, so a 2 GB upload is usually rejected long before it reaches your code.

LayerDefault limitWhat the user sees
nginxclient_max_body_size = 1 MB413 Request Entity Too Large. Also, by default nginx reads the whole body before forwarding it (proxy_request_buffering on), so even streaming apps receive nothing until nginx has the full file.
Cloudflare100 MB per request (Free/Pro plans)413 error from Cloudflare.
AWS API Gateway10 MB per request413 error; can't be raised.
AWS Lambda6 MB request payloadThe function is never invoked.
JavaA byte array holds at most ~2 GiBgetBytes() on a bigger file fails even if RAM is free.

IMPThis is why serverless and CDN-fronted apps must upload directly to storage. For them there is no “just raise the limit” option.

Abandoned uploads cost money

If a user starts a multipart upload and never finishes, the parts already uploaded stay in S3, invisible in the normal file list, and you're billed for them. Fix: a bucket lifecycle rule AbortIncompleteMultipartUpload (e.g. after 1 day), which tells S3 to delete unfinished uploads automatically.

Resuming after the user closes the laptop

  • With S3: save the uploadId (e.g. in the browser's storage). When the user returns, call ListParts, which lists the parts S3 already has, and upload only the missing ones.
  • With tus: an open protocol built just for resumable uploads. The client asks “how many bytes do you have?” (HEAD → Upload-Offset: 1,200,000,000) and sends the rest from that point (PATCH). Used by Vimeo, Cloudflare Stream and Supabase.

How big should each part be?

  • Smaller parts: a failure costs less to redo, but you make more requests.
  • Bigger parts: fewer requests, but a failure costs more.
  • For 2 GB: 64–100 MB parts (20–32 parts) is a good balance.
  • Parallel parts: 3–6 at a time is enough. More doesn't help, because they all share the same home connection.

Don't trust the file: the security pipeline

  • Quarantine first: new uploads land in a separate folder (quarantine/) that is never served to anyone. Only after the scan passes is the file moved to clean/.
  • Check the real type: a file named photo.jpg can be anything. Check the first bytes of the file (the “magic number”: every JPEG starts with FF D8 FF, every PDF with %PDF), not the name or what the browser claims.
  • Zip bombs: a tiny archive (a few KB) can expand to many GB when unzipped and crash the worker. Always unzip with a size limit and a time limit.
  • Rate-limit the “give me an upload URL” endpoint per user, so nobody can request thousands of URLs and fill your bucket.
  • Downloads have the same problem in reverse: serve big files with a presigned download link or a CDN, never by reading them through your app.

Same trap in other languages

  • Node/Express: multer.memoryStorage() keeps the whole file in RAM. Use disk storage, or stream with busboy. (For JSON bodies, express.json() rejects anything over 100 KB by default.)
  • Python: Django keeps uploads under 2.5 MB in memory and writes bigger ones to a temp file; FastAPI's UploadFile switches to a temp file above ~1 MB. That's safe for medium files, but a 2 GB file still passes through your server.
5 · Self-quiz

Check yourself (tap to reveal)

1. You added streaming and memory is now flat, but during big uploads the server stops answering other requests. Why?

Each upload still occupies one thread for the whole transfer, about 13 minutes for 2 GB at 20 Mbps. When enough uploads run at once, all threads in the pool are busy and every other request (login, search) has to wait.

2. You give users a presigned upload URL valid for 1 hour. What two things can go wrong?

(a) The URL works for anyone who has it: if it leaks, someone else can upload, again and again, for an hour. (b) A plain presigned upload URL doesn't limit file size, so someone could upload far more than 2 GB. Fix: 5–15 minute expiry, a server-chosen path, a size limit in the signature (POST policy or fixed number of parts), and a size check after upload.

3. A 2 GB upload is split into 21 parts. The Wi-Fi drops while part 14 is uploading. What gets uploaded again?

Only part 14 (and any other parts that were mid-upload at that moment). The parts already finished are safe in S3 under the same uploadId; ListParts tells the client which ones they are.

4. Your S3 bill keeps growing, but the number of files stays the same. What's a likely cause?

Unfinished multipart uploads. Their parts are stored and billed but never become visible files. A lifecycle rule AbortIncompleteMultipartUpload deletes them automatically after a set number of days.

5. Your backend runs on AWS Lambda behind API Gateway. Can you accept a 2 GB upload by streaming it?

No. API Gateway rejects requests over 10 MB and Lambda over 6 MB, before your code even runs. The only way is a direct upload to S3 with presigned URLs.
