API returns 1 million records, server dies

“Your API returns 1 million records in one response and the servers start failing. How do you fix it?”

The quick answer is “add pagination”. This page goes further: why LIMIT/OFFSET gets slower with every page and quietly shows duplicate rows, how keyset (cursor) pagination fixes both, the details that break naive cursor code, and what to do when someone really needs all 1 million rows (exports). Every term is explained the first time it appears.

Quick glossary

TermWhat it means
PaginationReturning a big list in small pages (say 20 rows) instead of all at once. The client asks for the next page when it needs it, like scrolling a feed.
LIMIT / OFFSETSQL for “skip this many rows, then give me that many”. LIMIT 20 OFFSET 40 = rows 41–60.
IndexA sorted lookup structure the database keeps next to a table (usually a B-tree), like the index at the back of a book. It lets the DB jump straight to “orders after 10 Jan” instead of reading every row.
Keyset pagination“Give me the 20 rows that come after the last one I saw”, using the sort column's value (e.g. WHERE id > 1040) instead of a row count to skip.
CursorThe bookmark the API hands the client for keyset pagination: usually the last row's sort values, encoded as an opaque string like eyJpZCI6MTA0MH0. The client just sends it back to get the next page.
SerializationTurning objects in memory into text (JSON) to send over the network. For big results this creates a second full copy of the data in memory.
StreamingSending the response piece by piece as rows are read, instead of building the whole thing first.
1 · Must-know

Why one big response kills the server

The innocent version: GET /orders → orderRepository.findAll() → return as JSON. Fine with 500 orders in testing. With 1 million:

1. The data is copied into memory several times

Say each order is about 1 KB as JSON. 1,000,000 × 1 KB ≈ 1 GB of JSON. But before that JSON exists, the server holds:

  • the rows the database driver fetched (many drivers fetch the whole result into memory by default: MySQL Connector/J does, and the PostgreSQL JDBC driver does unless you set a fetch size);
  • 1 million objects (Order entities), which in Java usually take several times the raw data size;
  • the full JSON string being built.

So one request can need several GB. Ten users calling it at once: OutOfMemoryError, and every other request on that server dies too. Same story in Node: one huge array plus one huge string, and the process runs out of heap.

2. The database and network suffer too

The DB reads 1 million rows for every call, pushing useful data out of its cache. The 1 GB response holds a connection for a long time and often hits a timeout first (an AWS load balancer's default idle timeout is 60 seconds).

3. The client can't use it anyway

A phone downloading and parsing 1 GB of JSON freezes or crashes. Nobody looks at row 700,000 in a list.

IMPRule: every list endpoint returns a bounded page, and the server enforces the maximum (e.g. limit ≤ 100), not the client. Otherwise someone sends ?limit=1000000 and you're back to square one.

2 · The half answer

LIMIT/OFFSET: works, until page 50,000

SELECT * FROM orders
ORDER BY created_at DESC
LIMIT 20 OFFSET 999980;   -- page 50,000

Problem 1: every page is slower than the last

The database can't jump to “row 999,980”. It has no idea where that is. It walks through 999,980 rows in order, throws them away, and returns the next 20. Page 1 touches 20 rows; page 50,000 touches about a million. An index on created_at makes the walk cheaper, but it's still a walk. Try it in the simulator below.

Problem 2: rows move under your feet

You load page 1 (newest 20 orders). While you read, 3 new orders arrive at the top. Now you ask for page 2 with OFFSET 20: everything has shifted down by 3, so the first 3 rows of page 2 are the last 3 you already saw. Duplicates. If rows get deleted instead, some rows slide past you and you never see them. For an infinite-scroll feed or a sync job, that's a real bug.

Where OFFSET is still fine

Small tables, admin screens, anywhere users need “jump to page 7” and nobody goes deep. It's simple and it supports page numbers, which keyset can't.

3 · Must-know

The real answer: keyset (cursor) pagination

Instead of “skip N rows”, say “start right after the last row I saw”:

-- first page
SELECT * FROM orders ORDER BY id LIMIT 20;
-- next page: last row on the previous page had id = 1040
SELECT * FROM orders WHERE id > 1040 ORDER BY id LIMIT 20;

Why it's fast at any depth

With an index on id, the database jumps straight to 1040 in the B-tree (a handful of reads, like opening a dictionary at the right letter) and reads the next 20 entries. Page 1 and page 50,000 cost the same.

Why it doesn't duplicate or skip

New rows inserted elsewhere don't change what “after id 1040” means, so nothing shifts between pages.

IMPThe detail most answers miss: ties

Feeds sort by time, not id. But many orders can share the same created_at. If page 1 ends in the middle of five orders created at 10:00:00, then WHERE created_at < '10:00:00' skips the rest of them forever. Fix: sort by the time plus a unique column as a tie-breaker, and compare both:

SELECT * FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- needs an index on (created_at, id)
-- portable form: created_at < :t OR (created_at = :t AND id < :id)

What the API looks like

GET /orders?limit=20
→ { "data": [ …20 orders… ], "nextCursor": "eyJ0IjoiMjAyNi0xMC0zMSIsImlkIjoxMDQwfQ", "hasMore": true }
GET /orders?limit=20&cursor=eyJ0IjoiMjAyNi0xMC0zMSIsImlkIjoxMDQwfQ
  • The cursor is just the last row's (created_at, id), encoded (here base64 JSON). Keeping it opaque lets you change the internals later without breaking clients.
  • hasMore trick: ask the DB for limit + 1 rows. If 21 come back, there's a next page; return 20.
  • Real examples: Stripe's API uses starting_after=<last object id>; GraphQL's Relay connections return endCursor and hasNextPage.

“Cursor” vs “keyset”: same thing

Some answers list them as two different techniques. Keyset is the SQL (WHERE (created_at, id) < …); cursor is how the API hands that position to the client. Same idea, two names.

What keyset can't do

  • No “jump to page 37”. Only next (and previous, by flipping the comparison and sort). Fine for feeds and infinite scroll.
  • Every sort option needs its own index. “Sort by price” needs (price, id).
  • Total count is expensive. COUNT(*) on a huge table reads a lot (in PostgreSQL it has to check each row's visibility). Show “1,000+” or an estimate instead of an exact “Page 1 of 50,000”.
4 · Deep extras

When someone really needs all 1 million rows

A finance team wants a CSV export of every order. Paging through 50,000 API calls is silly. Two good options:

① Stream it

Read rows from the database in batches and write each one to the response as you go (CSV or newline-delimited JSON), so memory stays flat: only one batch is in RAM at a time. Two details people miss:

  • The driver must stream too. PostgreSQL JDBC streams only with a fetch size set and auto-commit off; MySQL Connector/J needs useCursorFetch=true (or its special streaming mode). Otherwise the driver quietly loads all 1 million rows first.
  • It still holds a connection and a DB transaction for the whole download. Fine for a few exports, not for thousands of users.

② Make it a background job (best for big exports)

The API replies immediately: 202 Accepted, exportId = 77. A worker builds the file, uploads it to S3, and the user gets a temporary download link (a presigned URL, the same idea as in short 01) by email or notification. The API server never holds the data.

Same problem in search engines

Elasticsearch refuses deep from/size paging by default: index.max_result_window is 10,000. Its answer is the same as keyset: search_after with the last hit's sort values.

5 · Interview traps

Answers that sound right but aren't

“Cache the 1 million records in Redis.”

Then you're sending 1 GB from Redis instead of from the database: same memory and network problem on your API server. (And a single Redis string value can't exceed 512 MB anyway.) Caching helps repeated small reads, not huge responses.

“Add an index, OFFSET will be fast.”

An index lets the DB walk the rows in order without sorting, but OFFSET still walks and discards every skipped row. Deep pages stay slow.

“Rate-limit the endpoint.”

That limits how often it's called, not how much each call returns. One call still loads a million rows.

“Cursor using only created_at.”

Rows with identical timestamps at a page boundary get skipped. Always add a unique tie-breaker (id).

“Let the client choose the page size.”

Let it choose, but cap it on the server. ?limit=1000000 must become 100.

6 · Self-quiz

Check yourself (tap to reveal)

1. Page 1 of your list API takes 5 ms, page 40,000 takes 3 seconds. Same query, same index. Why?

OFFSET: the database walks and throws away all the rows before the requested page, so cost grows with the page number. Switch to keyset pagination.

2. Users scrolling the feed sometimes see the same post twice. What's happening?

OFFSET pagination plus new posts arriving at the top: everything shifts down, so the next page starts with rows already shown. Keyset pagination doesn't shift.

3. Your cursor is just created_at. What bug will you eventually see?

Rows sharing the boundary timestamp are skipped. Use (created_at, id) with an index on both.

4. You stream an export with a JDBC fetch size of 1000, but memory still explodes. Why might that be?

The driver ignored the fetch size: PostgreSQL's driver needs auto-commit off, MySQL's needs useCursorFetch=true (or streaming mode). Otherwise it loads the whole result first.

5. How do you know there's a next page without running COUNT(*)?

Fetch limit + 1 rows. If you got the extra one, hasMore = true; return only limit rows.
