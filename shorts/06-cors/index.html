Works in Postman, fails in the browser

“The API works perfectly in Postman. From the React app on localhost:3000, the console shows a red CORS error. Same API, same request. Why, and how do you fix it?”

Short version: the browser, not the server, is blocking it. The server has to send headers that say “this origin is allowed”, and for many requests the browser first asks permission with a preflight.

Quick glossary

TermWhat it means
OriginScheme + host + port. https://app.com and https://api.app.com are different origins. So are localhost:3000 and localhost:8080.
Same-origin policyA browser rule: JavaScript loaded from one origin can't read responses from another origin, unless that other server allows it.
CORSCross-Origin Resource Sharing: the response headers (Access-Control-Allow-*) a server uses to allow other origins.
PreflightAn automatic OPTIONS request the browser sends before the real one, asking “may I send this?”
1 · Must-know

Why Postman works and the browser doesn't

Postman isn't a browser

The same-origin policy exists only in browsers. Postman, curl and your backend servers ignore it, so the request just works there.

Why browsers have the rule

You're logged in to your bank, so the browser holds the bank's cookie. Without this rule, any website you open could run fetch('https://bank.com/balance'): the browser would attach your cookie, and that site could read your balance. The rule protects the user, not the server.

IMPThe server usually did receive and process the request. The browser just won't hand the response to your JS. CORS is enforced by the browser and fixed on the server.

2 · Must-know

Simple request vs preflight

Simple request: sent directly

GET, HEAD or POST, with only basic headers, and a Content-Type of form data or text/plain. The browser sends it and then checks the response for Access-Control-Allow-Origin. If it's missing → error, and the response is hidden.

Anything else: preflight first

PUT / DELETE / PATCH, Content-Type: application/json, or an Authorization header. That means almost every modern API call.

OPTIONS /orders Origin: https://app.com Access-Control-Request-Method: POST Access-Control-Request-Headers: content-type, authorization 204 Access-Control-Allow-Origin: https://app.com Access-Control-Allow-Methods: GET, POST, PUT, DELETE Access-Control-Allow-Headers: content-type, authorization Access-Control-Max-Age: 600

Only if this answer allows it does the browser send the real POST.

3 · Half answer

“Add Access-Control-Allow-Origin: *”

It fixes the simplest case, but:

  • With cookies / credentials, * is not allowed: the browser rejects it.
  • It doesn't answer the preflight: Allow-Methods and Allow-Headers are missing.
  • It opens your API to every website, which is too broad for anything private.
4 · Real answer

Fix it on the server, properly

① An allow-list of origins

If the request's Origin is in your list, send it back in Access-Control-Allow-Origin, plus Vary: Origin so caches/CDNs don't serve one origin's answer to another.

② Answer the preflight

Return 204 for OPTIONS with Allow-Methods, Allow-Headers, and Max-Age (caches the preflight so it isn't sent before every call).

IMP③ CORS middleware before auth

The most common real bug: the browser never sends cookies or the token with a preflight. If auth runs first, it returns 401 to the OPTIONS, the preflight fails, and it looks like a CORS problem.

④ With cookies

Server: Access-Control-Allow-Credentials: true + the exact origin (not *). Client: fetch(url, {credentials: 'include'}).

⑤ Or avoid CORS completely

Serve the frontend and API from the same origin through a reverse proxy (app.com/api → backend). In development, the Vite / CRA dev-server proxy does the same.

5 · Interview traps

Answers that sound right but aren't

“Fix it in the frontend.”

The frontend can't give itself permission. The headers must come from the server (or use a proxy, so it becomes same-origin).

“Use mode: 'no-cors'.”

The error disappears, but you get an opaque response: status 0 and an empty body. Your JS still can't read it.

“Echo back whatever Origin comes in, with credentials.”

That lets any site read your logged-in users' data. This is a real security hole. Use an allow-list.

“CORS protects the API from attackers.”

No. curl and scripts ignore it completely. Protect the API with authentication, authorization and rate limiting.

“Install a disable-CORS browser extension.”

Works only on your machine. Your users still get the error.

6 · Self-quiz

Check yourself (tap to reveal)

1. app.com calls api.app.com. Same origin?

No: the host is different. CORS applies.

2. Why does a JSON POST trigger a preflight but a form POST doesn't?

application/json isn't one of the “simple” content types, so the browser asks first.

3. The Network tab shows OPTIONS → 401. What's wrong?

Auth middleware runs before CORS. The preflight carries no token, so it's rejected. Move CORS first.

4. You set Allow-Origin: * and send cookies. Why does it still fail?

With credentials the browser requires the exact origin and Allow-Credentials: true.

5. Did the server execute the request that failed with a CORS error?

For a simple request, usually yes. The browser only hid the response. For a failed preflight, the real request was never sent.
