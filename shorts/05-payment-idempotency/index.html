Money deducted, but payment failed

“The app says Payment failed, but ₹2,000 has left the user's bank account. The user taps Pay again. How do you make sure they aren't charged twice, and the first ₹2,000 isn't lost?”

Short version: a timeout doesn't mean the payment failed, a retry must not charge twice (idempotency key), and a daily job catches whatever slipped through (reconciliation).

Quick glossary

TermWhat it means
IdempotentDoing it 2 times gives the same result as doing it once. A lift button is idempotent: press it 5 times, one lift comes.
Idempotency keyA unique ID (e.g. a UUID) the client sends with a request. If the server has already seen that key, it doesn't redo the work. It returns the first result.
Payment gatewayThe middle layer (Razorpay, PayU, Stripe) between your server and the bank / UPI.
WebhookThe gateway calls your URL later to say “payment X is now SUCCESS / FAILED”.
ReconciliationMatching your own payment records against the bank's or gateway's report (the settlement file) and fixing every mismatch.
1 · Must-know

How the money “disappears”

App ──▶ Your server ──▶ Gateway ──▶ Bank ✔ ₹2,000 debited App ◀────── Your server ◀─✘── Gateway ◀──── Bank reply lost / timed out

The debit worked. Only the reply got lost.

A network drop or a 30 s timeout between the gateway and your server. Your server never hears “success”, so it marks the payment “failed”. But the bank has already moved the money.

Not the same thing: the user kills the app

Then only server → app breaks. Your server still gets the reply and saves SUCCESS. The app just asks for the order status when it's reopened. The hard case is the one above, where your server itself doesn't know.

Now there are two dangers

  • The user pays again → charged twice.
  • Nobody follows up → ₹2,000 debited and no order. The user is angry.

IMPRule: a timeout means “I don't know”, not “failed”. Treating unknown as failed causes this whole problem.

2 · Half answer

“Just retry the payment”

Retrying is right. A blind retry is wrong: the first debit may have gone through, so the retry debits again. Retries are only safe when the server can tell “this is the same payment again”. That is exactly what an idempotency key does.

3 · Real answer

Four pieces

① State machine, with PENDING

CREATED ──▶ PENDING ──▶ SUCCESS └──▶ FAILED

On a timeout the payment stays PENDING. The app shows “Payment processing, we'll update you”, not “failed”. It moves to SUCCESS or FAILED only when there's proof.

② Idempotency key on every payment request

A retry with the same key returns the first result instead of charging again. Details in section 4.

③ Find out the truth

  • Webhook from the gateway with the final status. Verify its signature; the handler must be idempotent too (the same webhook can arrive twice).
  • Status poll: a job that asks the gateway “what happened to payment X?” for anything PENDING for more than a few minutes.

④ Reconciliation job (the safety net)

Daily: compare your DB with the gateway's / bank's settlement report.

  • Debited, but no order → complete the order or auto-refund.
  • Marked paid, but no debit → flag it for someone to check.

IMPIndia: RBI's turnaround-time rules say a failed UPI debit must be reversed by T+1 (the next day), or the bank pays ₹100/day compensation. (verify the current circular before quoting it)

4 · Must-know

How the idempotency key works

Who makes the key, and when

The client creates it once per checkout (e.g. Idempotency-Key: 7f3c… header) and reuses the same key on every retry of that checkout. If the server created it, a retry would arrive with no key, and the server couldn't connect the two requests.

What the server does

Request arrives with key K INSERT K, status = IN_PROGRESS (unique constraint on K) ├─ insert worked → charge, save the response against K, return it └─ K already there → COMPLETED? return the saved response, no new charge IN_PROGRESS? return 409 "still processing"

Table: idempotency_keys(key PRIMARY KEY, request_hash, status, response, created_at). Old keys are cleaned up after ~24 h.

IMPThe race most answers miss

Two retries arrive at the same moment. With “check if the key exists, then insert it”, both checks see nothing → both charge. The fix is to let the unique constraint decide (or Redis SET K NX): only one insert can win. Same idea as Day 2's oversold item.

Same key, different body?

Store a hash of the request. Same key with a different amount → reject it (Stripe returns an error). Otherwise a bug could silently return an old payment's result.

Pass it down

Send the same key (or your order ID) to the gateway too, so the gateway also refuses a second charge. Stripe supports an Idempotency-Key header directly.

5 · Interview traps

Answers that sound right but aren't

“Wrap it in a DB transaction.”

The bank call is outside your database. A rollback can't undo money that the bank has already moved.

“Retry with exponential backoff.”

Good for when to retry. Without an idempotency key every retry is still a new charge.

“New key every time the user taps Pay.”

Then every tap looks like a new payment. One key per checkout / order.

“Check the key in Redis, then process.”

Check-then-act is a race. Use an atomic insert (SET NX or a unique constraint).

“POST is idempotent if we're careful.”

By definition GET, PUT and DELETE are idempotent and POST isn't. That's why POST needs a key.

6 · Self-quiz

Check yourself (tap to reveal)

1. The gateway call timed out. What status do you save?

PENDING. Then the webhook, the status poll or reconciliation decides the final state.

2. Two requests with the same key arrive 5 ms apart. What stops a double charge?

The unique constraint on the key: the second insert fails, so it returns 409 or the saved response.

3. Why must the client generate the key?

Only the client knows that two requests are the same checkout. A server-made key is new on every request.

4. The webhook says SUCCESS twice for the same payment. What happens?

Nothing the second time: the handler checks that it's already SUCCESS (or dedupes by event ID) and ignores it.

5. The bank debited, there's no webhook, and the poll failed too. Who catches it?

The daily reconciliation job: debited with no order → complete it or refund.
